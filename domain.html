Literature survey

The entries below are the related-work set written in the project reference file. Each note says only how that source is used in the project notes. Experimental claims from the papers themselves are not restated here.

Object detection

Redmon et al. introduced YOLO as a unified real-time detector [2]. Bochkovskiy et al. describe YOLOv4 [3]. The implementation uses Ultralytics YOLO, cited as Jocher, Chaurasia, and Qiu [1].

Smart waste monitoring

Hannan et al. review technologies used in solid-waste monitoring [4]. Anagnostopoulos et al. survey waste management in IoT-enabled smart cities [5]. Folianto, Low, and Yeow present Smartbin [6]. Wijaya, Zainuddin, and Niswar design a smart waste bin [7]. Abdullah, Alwesabi, and Abdullah describe an IoT smart-waste system [8]. Vo et al. study YOLO-based detection for recyclable separation and trash-bin capacity [9].

Sensing, software, and data

The edge node uses an ESP32-CAM [10]. The mobile client uses Flutter [11]. Model services use FastAPI [12]. The fill dataset is Garbage_Fill_Level v2 on Roboflow, attributed to C. Edirisinghe [13]. Image handling uses OpenCV [14].

Not listed as cited documents. The reference file marks a Central Environmental Authority page and the UNEP Global Waste Management Outlook as optional local context, and it says to cite the specific PDF actually downloaded. No specific download is identified, so those two items are omitted.

Research gap

The project notes contrast ultrasonic-only smart bins [6], [7] with fill state estimated from imagery, in the spirit of vision-assisted recycling systems [9], but aimed at Empty, Half, and Overflow tiers for public bins. VisionWaste then joins that fill estimate with waste type, animal presence, outside-bin litter, and weather.

The same overview records limits that the work does not claim to have closed: the waste model is binary, so a mixed-waste critical case cannot be inferred from one image; the hygienic-risk forecast does not predict new animals or a cleaning crew; and litter weights were missing at the 30 August 2026 evaluation, so the litter severity index was skipped in that run.

Research problem

Avoiding inconvenience to people due to irregular waste.

That line is the repository title and the stated goal of the system overview. The implemented response is a readable hygienic-risk level, staff alerts and collection support, citizen nearest-bin lookup, and optional audio at the bin.

Research objectives

These objectives are taken from the functions described in the technical overview. Replace them if the official proposal states different wording.

  1. Classify waste in a captured image as organic or non-organic.
  2. Detect cat, crow, dog, and monkey at the bin.
  3. Estimate bin fill as Empty, Half, or Overflow.
  4. Score litter outside the bin with a litter severity index from 0 to 100.
  5. Detect a littering event in a frame, as a service separate from litter severity.
  6. Combine waste type, animals, and weather into an explicit risk case and message.
  7. Store the capture, raise alerts, and support maps, forecasts, and collection stops.

Methodology

Machine learning does not run inside the Express gateway. Each model is its own process. The browser and the phone talk only to the gateway. The gateway talks to the model services over HTTP.

  1. 01EdgeESP32-CAM captures a JPEG. A PIR sensor and a DFPlayer are part of the documented edge node. A laptop bridge is required when the camera is only on a private network.
  2. 02GatewayPOST /predict accepts a multipart image from an ESP32, a phone, or an admin upload. Weather uses request GPS, else the bin coordinates, else Colombo defaults 6.9271, 79.8612.
  3. 03ModelsWaste, animal, fill, litter severity, and littering action are separate services. Fill classes are Empty, Half, and Overflow.
  4. 04Risk and responseRules set the level. Postgres can store the capture and alerts. High and critical ESP32 results can queue DFPlayer tracks.

Hygienic risk rules

The engine is rule-based. Thresholds recorded in the overview are 30°C and 70% humidity. Case 4, mixed waste plus animals, is not implemented.

Litter severity index

The documented fusion is about 0.5 times litter count, plus 0.32 times area, plus 0.18 times spread. Low is 30 or below, medium is 53 or below, and high is above that. An optional bin polygon drops detections whose centroid is inside the bin.

Two different forecasts

The hygienic-risk timeline replays the same rule engine on future weather slots. It assumes the waste type stays until the bin is cleaned, the animal count stays at the current value, and hours since cleaning grow linearly. It does not predict new animals.

A separate XGBoost pipeline forecasts municipal waste kilograms by location and category. That model is not the hygienic-risk timeline.

Technologies used

ESP32-CAMOV2640 JPEG capture at the bin, with a laptop bridge for private-network access.
PIR and DFPlayerMotion input and speaker tracks. High maps to track 2 and critical to track 3, with a 60-second cooldown.
MobileNetV2TensorFlow waste classifier: organic or non-organic.
YOLOv8Animal detection and the YOLOv8n fill detector.
YOLO11Litter severity and a separate littering-event detector.
FastAPI and FlaskModel microservices. The fill service has also been run as Flask.
Express.jsAPI gateway, risk rules, alerts, and device commands. No model weights in the gateway.
React and FlutterStaff and public web UI, plus an Android app for nearest bins and staff routes.
PostgreSQLUsers, devices, captures, predictions, and alerts. Inference still runs if the database is absent.
XGBoostMunicipal waste-kilogram forecast, separate from the risk-rule timeline.
